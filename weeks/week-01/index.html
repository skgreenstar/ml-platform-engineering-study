Beyond
Model Accuracy.

좋은 모델을 만드는 것과, 신뢰할 수 있는 AI 시스템을 운영하는 것은 다른 문제다. ML 플랫폼을 모델의 '실행 장소'가 아닌 지속적인 학습·배포·검증을 가능하게 하는 제품으로 바라본다.

Week 01 · 2026.10 · AI Engineering 관점의 학습 노트
CORE THESIS

Model quality ≠ System quality

실제 서비스 품질은 모델 정확도만이 아니라 데이터, 재현성, 배포 안전성, 지연시간, 비용, 관측 가능성의 합성 결과다.

이 글은 1주차 CH1~CH2와 연계한 독립 학습·실무 확장 글입니다. 원문 강의 노트 전체를 검증한 축약본은 아니며, 사례는 특정 회사·고객을 식별할 수 없도록 일반화했습니다. 실습 수행 여부를 주장하지 않습니다.

01. 왜 ML은 배포 이후가 더 어려운가

노트북에서 얻은 평가 점수는 통제된 데이터셋과 실행 환경의 결과다. 운영 환경에서는 데이터 생성 과정이 달라지고, 추론 입력의 결측·지연·스키마 변경이 발생하며, 사용자의 요구도 변한다. 따라서 학습 결과를 파일로 저장해 API에 올리는 것만으로는 시스템이 완성되지 않는다.

EXPERIMENT

Can it predict?

오프라인 데이터와 고정된 평가 프로토콜에서 모델의 예측력을 측정한다.

PRODUCTION

Can we trust it?

입력 변화, 오류, 트래픽, 비용과 회귀(regression)를 포함해 운영 가능한지를 확인한다.

핵심 전환: 모델을 산출물로 관리하는 것에서, 모델이 포함된 시스템의 생명주기를 관리하는 것으로.

02. ML Platform Engineering의 책임 경계

플랫폼은 단순히 Kubernetes 클러스터나 GPU 서버를 제공하는 팀의 일이 아니다. 반복되는 인프라 작업을 표준화해 ML 엔지니어가 실험, 검증, 배포에 집중하도록 만드는 내부 제품이다. 표준 인터페이스와 자율성을 제공하되, 과도한 추상화로 디버깅 가능성을 잃지 않아야 한다.

개념적 플랫폼 레이어. 특정 도구에 종속되지 않는 논리 아키텍처.

플랫폼의 성공 기준도 '도구를 몇 개 설치했는가'가 아니라 실험 재현 시간, 배포 리드타임, 실패 복구 시간, 품질 저하 감지 속도 등으로 잡는 편이 유용하다.

03. 재현성은 코드 버전만으로 완성되지 않는다

같은 코드라도 데이터 스냅샷, 피처 생성 시점, 라이브러리, 랜덤 시드, 하이퍼파라미터가 달라지면 결과가 달라질 수 있다. 재현 가능한 실행을 위해서는 최소한 다음의 식별자가 연결되어야 한다.

run_id → code_commit → data_snapshot → feature_spec
       → environment → hyperparameters → metrics
       → model_artifact → deployment_revision

실험 추적은 '최고 점수'를 찾기 위한 로그가 아니라, 운영 이슈 발생 시 어떤 변경이 결과를 만들었는지 역추적하기 위한 증거 체계다. MLflow와 같은 도구는 실험 추적·모델 관리의 중심이 될 수 있지만, 데이터 품질 검사와 배포 정책은 별도 설계가 필요하다.

CH3 학습과 연결되는 개념도. 실제 구축 완료를 의미하지 않음.

중요한 것은 자동화의 범위보다 실패했을 때 안전하게 멈추고 되돌릴 수 있는가다. 재학습 모델은 오프라인 성능만으로 자동 승격하지 않고 데이터 품질·안전성·서비스 요구사항을 함께 검증해야 한다.

05. 제조 ML: 낮은 오차가 높은 신뢰성을 보장하지 않는다

산업 시계열과 회귀 모델에서는 MAPE가 낮아도 실제 운전 조건에서 의미 있는 변화량을 포착하지 못할 수 있다. 목표 변수의 변동폭이 좁으면 평균에 가까운 예측만으로 MAPE가 좋아 보일 수 있고, 반대로 R²는 낮게 나타날 수 있다.

DESIGN REVIEW · GENERALIZED

운영 가능성을 묻는 네 가지 질문

① 데이터가 학습 범위를 벗어났는가? ② 파생변수에 미래 정보가 섞였는가? ③ 특정 운전 구간별 오차가 커지는가? ④ 예측값을 실제 의사결정에 사용할 수 있는가?

특히 피처 리키지는 학습 시점에만 관측 가능한 값이 추론 시점에 존재한다고 가정할 때 발생한다. 무작위 분할보다 시간 기반 검증과 피처 가용 시점(point-in-time)을 확인해야 하는 이유다. 평균 지표뿐 아니라 구간별 오류·예측 편향·불확실성을 함께 보고, 모델을 사용할 수 없는 조건도 명시해야 한다.

06. LLMOps: 모델이 아니라 파이프라인 전체가 제품이다

RAG와 Agent는 기반 LLM을 고정해도 데이터 수집, 청킹, 임베딩, 인덱스, 검색기, 재정렬, 프롬프트, 도구 호출이 달라지면 출력이 바뀐다. 따라서 LLM 버전만 기록하는 것으로는 결과를 재현할 수 없다.

Agent는 단계별 성공률을 따로 측정해야 한다. 최종 답변만 평가하면 검색 실패, 잘못된 도구 선택, 권한 문제 중 무엇이 원인인지 파악하기 어렵다.

07. Evaluation & Observability: 점수보다 원인 추적

LLM 기반 서비스에서는 RAGAS 등 자동 평가, 도메인별 골든셋, 사람의 평가를 상호 보완적으로 사용한다. Faithfulness는 답변이 주어진 근거에 충실한지 평가하는 관점이지, 외부 세계의 사실성을 자동으로 보장하는 지표는 아니다.

QUALITY

Offline Evals

고정된 평가셋, 회귀 테스트, 시나리오별 실패 유형을 추적한다.

RUNTIME

Traces & Metrics

요청별 검색·생성·도구 호출 지연, 오류율, 비용을 관찰한다.

Langfuse 같은 추적 도구를 사용할 때도 민감 데이터 마스킹, 보존 기간, 권한 정책을 함께 설계해야 한다. 관측 가능성은 모든 데이터를 무제한 저장하는 것과 다르다.

08. 운영 설계는 트레이드오프의 기록이다

Quality × Reliability × Latency × Cost — 네 요소를 동시에 무한히 최적화할 수는 없다.

큰 모델은 품질 개선 가능성이 있지만 비용·지연시간이 증가할 수 있고, 검색 Top-K를 높이면 재현율이 개선되는 대신 노이즈와 컨텍스트 비용이 증가할 수 있다. 단일 모델 성능보다 서비스 수준 목표(SLO), 예산, 장애 복구 전략을 먼저 정의하는 편이 합리적이다.

내가 정리한 실무 설계 원칙은 다음과 같다.

  1. 검증 가능한 변경: 데이터·모델·프롬프트·인덱스를 릴리스 단위로 묶는다.
  2. 안전한 배포: 자동 평가, 단계적 노출, 롤백 기준을 둔다.
  3. 원인 추적: 예측 결과만이 아니라 실행 경로를 관찰한다.
  4. 목적에 맞는 복잡도: 작은 서비스에 과도한 플랫폼을 강요하지 않는다.

09. 다음 주: MLflow, Feast, Kubeflow

다음 단계에서는 MLflow로 실험과 모델 아티팩트를 추적하고, Feast로 학습·서빙 피처의 일관성을 살펴보고, Kubeflow로 Kubernetes 위에서 ML 워크플로를 구성하는 방법을 학습할 계획이다. 이번 주의 K8s·CI/CD 환경은 이후 실습의 기반이므로 별도로 검증한다.

WEEK 01 TAKEAWAY

운영 가능한 AI는 모델 파일이 아니라 변경 가능한 시스템이다.

이번 학습에서 얻은 핵심은 도구 목록이 아닌 설계 기준이다. 데이터에서 응답까지 이어지는 경로를 재현하고, 평가하고, 되돌릴 수 있을 때 비로소 지속 가능한 AI 서비스가 된다.
